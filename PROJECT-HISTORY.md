# Project history

GENESIS grew through human-directed engineering missions. The owner specified objectives and boundaries; Codex inspected existing tools, implemented scoped changes, tested results and retained evidence. Each stage extended earlier work.

The results below are historical snapshots from 26–27 October 2026. Source reports are identified in the [knowledge index](KNOWLEDGE-INDEX.md#evidence-sources).

## GENESIS-1 — Trading controller

A deterministic Python controller brought research, synthetic simulation, public market data, journaling and reporting behind explicit commands. Its separate official cTrader CLI integration supported bounded, authorized demo workflows. Broker identity checks, durable intent and reconciliation helped keep uncertain results from being blindly resent.

Research results, simulations and broker-confirmed demo activity were recorded separately. This stage supplied reusable research and simulation interfaces for later work; it did not prove profitable trading.

## GENESIS-2 — Ten-project trading research laboratory

The laboratory acquired ten independent upstream projects: NautilusTrader, Freqtrade, Jesse, VeighNa, LEAN, TradingGym, TradingGoose-Studio, ta4j, OpenStock and Qbot.

Separate environments and provenance records preserved their independence. All ten received representative local functional verification; seven recorded builds, while three retained partial optional functionality. Acquisition, dependency readiness, compilation, launch and functional proof remained separate states. Demonstrations used public or synthetic data and placed no broker orders.

## GENESIS-3 — Software capability registry

The registry made installed software discoverable through version, executable, environment, dependency and verification records. The recorded refresh preserved 1,402 earlier entries while extending the inventory to 1,644 component/evidence records.

JSON and TOML inventories, a readable summary and persistent Codex pointers encouraged reuse before installation. An installation record was never treated as proof that a workload worked.

## GENESIS-3.1 — Capability intelligence engine

Python and SQLite added relationships, routing, dependency reasoning and reusable workflow history to the registry. The first report recorded 1,687 nodes and 321 relationships. The later advanced snapshot recorded 1,807 nodes, 496 relationships, 47 workflows, 92 outcomes and 20 causal cases over a 1,645-record inventory.

The advanced engine added multi-step paths, tool composition, failure prevention and adaptive verification. Its scoped suite passed 131 tests and ten acceptance scenarios. Newer failures could influence routing without erasing older successful evidence. These are dated engineering counts, not a promise about the present state of any computer.

## GENESIS-4 — AI-native financial-control infrastructure

The Financial Control Hub combined simulated accounts, payments, transaction recovery, trading research, a SQLite ledger, a local API, dashboard and MCP tools. It reused earlier research code, environments and capability knowledge.

Recorded acceptance demonstrated a synthetic EUR 100.00 deposit and EUR 25.00 purchase leaving EUR 75.00, with balanced entries, reconciliation and repeat protection. The run passed 74 hub tests and 305 active workspace regressions. Real financial-provider connectors remained unimplemented; SQL Server was a separately tested snapshot adapter.
